# Architecture Overview

The restaurant module is modeled around `User` as the main business resource and `Restaurant` as a child resource.

```mermaid
classDiagram

        String lastName

    }

    class Restaurant {

    }
```

Recommended Spring Boot responsibility split:

```mermaid
flowchart LR
    Client --> RestaurantController

    RestaurantController --> RestaurantService

    RestaurantService --> RestaurantRepository
    RestaurantService --> UserService 

    UserService --> UserRepository

    RestaurantRepository --> DB[(DataBase)]
    UserRepository --> DB
```

### Controller responsibilities

- `RestaurantController`
    - Add a restaurant.
    - Update a restaurant.
    - Remove a restaurant.
    - view a restaurant.

### Service responsibility

`RestaurantService` owns user business operations.

# API Conventions

Base path:

```text
/api/v1
```

Current customer-scoped cart path:

```text
/api/v1/restaurant
```

General rules used by this API:

1. Resource identity belongs in the URL.
2. Operation data belongs in the request body.
3. `restauantIs` and `userId` are generated by the backend. 
4. All properties must be not bull except description of restaurant

# Validation and Error Handling

Request DTO validation uses Jakarta Bean Validation. 

Example:

```text
        @NotNull(message = "the id of restaurant is required")
        UUID restaurantId,
        @NotNull(message = "the restaurant's code is required")
        String restaurantCode,
        @NotNull(message = "the restaurant's name is required")
        String restaurantName,
        String restaurantDescription,
        @NotNull UpdateUserRequestDto userRequestDto
```

A global validation handler can collect field errors:

```java
@ExceptionHandler(MethodArgumentNotValidException.class)
public ResponseEntity<ErrorResponse> handleValidationException(
        MethodArgumentNotValidException ex) {

    String errors = ex.getBindingResult()
            .getFieldErrors()
            .stream()
            .map(error ->
                    error.getField() + ": " + error.getDefaultMessage()
            )
            .collect(Collectors.joining(", "));

    ErrorResponse response = ErrorResponse.builder()
            .status(HttpStatus.BAD_REQUEST.name())
            .message(errors)
            .timestamp(LocalDateTime.now())
            .build();

    return ResponseEntity
            .status(HttpStatus.BAD_REQUEST)
            .body(response);
}
```

Generic internal server errors should not expose internal implementation details:

```java
@ExceptionHandler(Exception.class)
public ResponseEntity<ErrorResponse> handleInternalServerError(
        Exception ex) {

    log.error("Unhandled exception occurred", ex);

    ErrorResponse response = ErrorResponse.builder()
            .status(HttpStatus.INTERNAL_SERVER_ERROR.name())
            .message("An unexpected error occurred")
            .timestamp(LocalDateTime.now())
            .build();

    return ResponseEntity
            .status(HttpStatus.INTERNAL_SERVER_ERROR)
            .body(response);
}
```

Recommended error mapping:

| Condition                        | HTTP |
|----------------------------------|---|
| Invalid request body             | `400 Bad Request` |
| Restaurant not found / not owned | `404 Not Found` |
| Restaurant existence             | `409 Conflict` or domain-specific `400` |
| Unexpected server error          | `500 Internal Server Error` |

## Relationship Mapping

Recommended relationship:

```java
@Entity
public class User {
  @Id
  @GeneratedValue(strategy = GenerationType.UUID)
  private UUID userId;

  @Column(name = "first_name")
  private String firstName;

  @Column(name = "last_name")
  private String lastName;

  @Column(name = "phone_number")
  private String phoneNumber;

  @Column(name = "user_password")
  private String userPassword;
}
```

```java
@Entity
public class Restaurant {
  @Id
  @GeneratedValue(strategy = GenerationType.UUID)
  private UUID restaurantId;

  @Column(name = "restaurant_code",nullable = false, unique = true)
  private String restaurantCode;

  @Column(name  = "restaurant_name")
  private String restaurantName;

  @Column(name = "restaurant_description")
  private String restaurantDescription;

  @OneToOne(cascade = CascadeType.ALL)
  @JoinColumn(name = "user_id")
  private User user;
}
```

`Restaurant` owns the relational foreign key because `restaurant.user_id` is physically stored in the child table.

# Summary

The cart API follows these core design decisions:

```mermaid
flowchart LR
    A[Customer-scoped REST API] --> B[Thin Controllers]
    B --> C[CartService]
    C --> D[Ownership-aware repository queries]
    C --> E[Server-authoritative menu data]

    D --> F[(PostgreSQL)]
    E --> G[Mock Menu Catalog for now]

    C --> H[Validation]
    C --> I[Transactional business operations]

    D --> J[Bulk DELETE where appropriate]
    I --> K[Hibernate dirty checking for managed updates]
```

The most important rules are:

- Keep `customerId` in the path only until authentication is available.
- Never trust client-supplied price.
- Use `cartItemId` in the path when addressing an existing item.
- Keep quantity changes explicit with `PATCH`.
- Keep removal explicit with `DELETE`.
- Use one bulk database delete for batch removal and clear-cart operations.
- Enforce ownership inside repository predicates where practical.
- Keep `Cart` as the aggregate-level business concept even when controllers are separated.
